## Что изменено

Новая отдельная страница `landing-podryad.html`, стили `assets/css/landing-podryad.css`, скрипт `assets/js/landing-podryad.js`. Задачи: неоплата, сдача работ, риски договора; для каждой услуги указан результат. Уточнены согласование стоимости/срока и отсутствие гарантий исхода. Нет внешних шрифтов и библиотек; основной контент доступен без JavaScript. Отдельные стили не требуют пересборки основного Tailwind.

Форма использует существующий `api/process_form.php`, его имена полей и JSON-контракт. Ничего не меняется в БД, API, конфигурации, главной, генераторе или оплате. Ввод ограничен, согласие обязательно в интерфейсе, есть honeypot, блокировка повторного запроса, сохранение введённого при ошибке и различение сохранения заявки от доставки автоответа. Успех показывается только при HTTP 2xx и `success === true`. При неопределённом сетевом результате пользователь предупреждён о возможном сохранении, чтобы не создавать дубли.

**Ограничения существующего backend до запуска рекламы:** он не проверяет согласие на сервере и не хранит его версию/время, не сохраняет источник кампании, не возвращает ID заявки клиенту. Уведомление администратору уходит в Telegram для всех обращений, тогда как документы о данных описывают передачу через выбранный пользователем канал; согласовать фактическую обработку и документы с владельцем. Возможен сценарий сохранённой заявки без уведомления администратора. Требуется отдельная проверка и согласованная доработка после сравнения production; эти обработчики в данной работе не заменялись.

## Измерение заявок

Скрипт публикует `CustomEvent('contractor:goal', {detail})`:

| Событие `detail.event` | Значение |
| --- | --- |
| contractor_request_open | Переход к форме |
| contractor_service_select | Выбор услуги, service = contract/claim/arbitration |
| contractor_form_start | Начат ввод |
| contractor_form_submit | Отправлен валидный запрос, ещё не заявка |
| contractor_lead_saved | API подтвердил сохранение, ещё не продажа |
| contractor_form_error | Ошибка или неподтверждённый результат |
| contractor_telegram_click / contractor_email_click / contractor_bot_click | Переход в канал связи, не факт обращения |

События не содержат ФИО, контактов, вопроса, query string или UTM. Скрипт не подключает счётчик, не пишет cookies/localStorage, не передаёт события на внешний сервер. Без подключения приёмника события не сохраняются между посещениями. Фактическая аналитика пока НЕ включена.

Подключать к существующему согласованному счётчику после проверки production, настройки необходимых согласий и документов. Например, в коде интеграции после инициализации реального счётчика:

```js
window.addEventListener('contractor:goal', ({ detail }) => {
  // consentGranted и counterId задаются существующей системой сайта.
  if (consentGranted && typeof window.ym === 'function') {
    window.ym(counterId, 'reachGoal', detail.event,
      detail.service ? { service: detail.service } : {});
  }
});
```

Это пример, а не установленная интеграция. События подключать до взаимодействия; исключить двойную отправку с глобальными обработчиками сайта. Настроить цели и проверить их в отладчике счётчика. UTM-атрибуция в БД, CRM, квалификация и оплата не реализованы: нужен существующий механизм связывания по ID заявки/заказа. Статус оплаты брать только из подтверждённого сервером платёжного события, а не из браузерного перехода. Для Telegram/email владелец должен проверить получение и отдельно учитывать состоявшееся обращение.

## Безопасная публикация на Beget

README изучен. Его шаг «загрузить файлы в public_html и импортировать схему» применим к НОВОЙ установке, не к действующему сервису. В данном случае не выполнять его поверх production.

1. В панели Beget установить точный document root домена, PHP-версию/расширения, привязанную БД, cron-задачи и размещение генератора/оплаты. Проверить актуальный backup хостинга. Секреты вводить только через защищённые настройки, не в чат и не в Git.
2. До любых изменений создать закрытую резервную копию всего document root (включая dotfiles), uploads, шаблонов/сгенерированных документов и файлов вне public_html, от которых зависит приложение. Сделать согласованный дамп БД (для InnoDB — поддерживаемый consistent snapshot; учитывать другие движки и продолжающиеся записи). Включить существующий config/ключи в зашифрованную приватную копию с ограниченным доступом; не хранить её в webroot/Git. Проверить контрольные суммы, содержимое архива и восстановление на изолированной копии. Записать PHP-настройки, задания и webhook URL без значений секретов в отчёте.
3. Скачать приватную копию production для сравнения. Составить список путей/размеров/SHA-256, сравнить с репозиторием. Отдельно проверить `index.*`, `.htaccess`, `includes/config.php`, обработчики, пути `/uslugi/`, `/proverka/`, тарифы, privacy/consent, загрузки, генератор, платёжные endpoints и webhooks. Отличия не трактовать как устаревшие файлы: выяснить их назначение и сохранить. Не печатать diff секретов в общие логи. При невозможности сравнения остановить публикацию.
4. Развернуть копию вне работающего document root или на закрытом тестовом поддомене с отдельной тестовой БД и тестовыми ключами. Не регистрировать staging URL как webhook рабочего бота или платежей. Не запускать рассылки/cron production из копии. Настроить запрет индексации и ограничение доступа тестового сайта.
5. Проверить владельцем актуальные цены, каналы связи, объём услуг и юридические документы. Прогнать реальную тестовую заявку с согласованным адресатом: сохранение в тестовой БД, уведомление, ответ. Проверить существующую генерацию документа и sandbox оплату, webhook с проверкой подписи и идемпотентности, повторную доставку, неуспешную оплату. Реальные списания не делать без отдельного согласования. Проверить Apache-защиту служебных файлов, HTTPS и кеширование.
6. Подготовить минимальный release manifest: **только** `landing-podryad.html`, `assets/css/landing-podryad.css`, `assets/js/landing-podryad.js`. Сначала убедиться, что эти пути ещё не заняты или полностью сравнить существующие версии. Сначала загрузить CSS/JS, проверить их, затем опубликовать HTML атомарным переименованием в пределах файловой системы, если это поддерживается. Не менять главную, `.htaccess`, БД, конфиг, privacy/consent, sitemap/robots и обработчики пакетом. Не применять `rsync --delete`, не загружать весь checkout. Не публиковать `.git`, node_modules, tests, docs, config.example, SQL, архивы или секреты.
7. Проверить production страницу на мобильном устройстве, все ссылки, браузерную консоль, валидную заявку с согласованным получателем и получение цели аналитики. Проверить, что основной генератор и оплата продолжают работать. После подтверждения тарифов/правовых документов/каналов и целей снять `noindex`, при необходимости добавить URL в существующий sitemap отдельным изменением и проверить индексируемость. До этого рекламную кампанию не запускать.
8. Откат: сохранить до публикации предыдущие версии этих трёх файлов (или факт их отсутствия). При проблеме отключить рекламный трафик, вернуть прежние файлы/убрать только новые пути. БД в минимальном релизе не меняется; не восстанавливать старый дамп поверх новых заявок/платежей. Полный rollback выполнять по отдельному плану с учётом всех записей после backup.
